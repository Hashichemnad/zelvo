# Phase 2 build plan (proposed 2026-11-26, for the product owner's approval)

Phase 2 delivers modules 16–21 of [requirements.md](requirements.md): problem management, change management, the CMDB and asset management, the installable web app and Microsoft Teams, workflow automation and agent wellbeing. It also starts with a maintenance task for Phase 1 follow-ups. As in Phase 1, each task is one branch and one pull request, and each follows CLAUDE.md: plan first, build with tests, run in Docker Compose, update Progress.

**How to read it:** the **Parallel** column says which tasks can run at the same time (same wave, no dependency between them). Large modules are split so each pull request stays reviewable. Every UI task ships English and Arabic, right to left and WCAG 2.2 AA from the start; every API task ships OpenAPI documentation, audit logging, row-level security on its new tables and a demo seeder for both sample organisations (the requirements' "sample data grows with each phase").

**Branches and pull requests:** the Branch column names each task's scope only. The actual branch is the one the Claude Code session provides (`claude/...`), and the pull request title starts with the task ID, for example "G1: CMDB core".

**Product owner decisions of 2026-11-26 that shape this plan**

1. Phase 1 is approved for development to continue. Its **verification** (the load test on a test server, tests against real integrations, the product owner's own walkthrough) runs alongside Phase 2; what it finds is fixed in maintenance tasks (M1, M2 and further M tasks as needed).
2. The **external penetration test runs once, after all four phases**, before go-live. Each phase brings the penetration test pack (`docs/release-readiness/pentest-pack.md`) and the ASVS checklist up to date instead (task L1).
3. Module 19 is an **installable web app** (home-screen install with each customer's own name and icon, web push, camera attachments, offline-friendly) instead of native iOS and Android apps, which are deferred until customers ask. The **Microsoft Teams app stays** in scope.
4. Module 21: **agents see their own figures**; the dashboard supports workload balancing and is **not for ranking**; it follows the UAE Personal Data Protection Law.

**Parallel work and shared files:** tasks in the same wave touch shared files (translation files, `PermissionCatalog`, the demo seeders' order, the EF Core model snapshot, CLAUDE.md Progress). The second task to merge rebases on `main` first and regenerates its migration on top of the other's, never hand-merging the model snapshot.

### Proposed screen: Settings → Updates → Malware definitions (M1)

- **Status card:** "Malware scanning: on", the loaded definitions (daily version number and its date in the person's calendar and digits), last update (imported by whom and when, or downloaded automatically), and a red warning when they are older than the warning period.
- **Import:** a file picker for several files at once, or "Import from the updates inbox" listing the definition files found there; each file is listed with its type, version and date, and "Import" is enabled only when every file passed the checks; refusals give their reason (not a ClamAV file, older than the loaded version, `main` or `bytecode` missing on the first import, too large).
- **Settings:** the warning period in days (1–90, default 7) and, for installations with internet access, "Download definitions automatically" (on when ClamAV can reach ClamAV's own servers; off makes ClamAV read only the imported files).
- **History:** the last 20 imports and automatic downloads with their versions and outcome.

## Decisions needed from the product owner

Each has a recommendation; the tasks that need it are in brackets.

1. **Plan approval** — order, splitting, waves and scope per task (all).
2. **Hardened-install gaps** (M2): add task M2 for the first tenant administrator, several tenants and `/api/v1` through the proxy on hardened installs? *Recommended: yes, in wave 1*, because a real customer install needs them long before the penetration test.
3. **Malware definitions** (M1): approve the proposed screen and the **private mirror** approach (works on Compose and Kubernetes, ClamAV checks the signatures itself), rather than the updater copying files into ClamAV's volume (Compose only). *Recommended: private mirror, 7-day warning.*
4. **Discovery sources** (G2): which discovery tools to support first beyond the discovery API and file import? Options: Microsoft Intune (through Graph, reusing E7's Entra app), Microsoft Configuration Manager, Lansweeper, Azure and AWS resource inventories, VMware vCenter. *Recommended: discovery API + Intune + Azure and AWS inventories first.*
5. **Relationship map library** (G1): Cytoscape.js (MIT, layouts built in) or React Flow (`@xyflow/react`, MIT, needs a separate layout library). *Recommended: Cytoscape.js*, with the list view as the accessible equal.
6. **Who a change affects** (G1, H5): users and departments are linked to business services through a "used by" relationship (users, departments, customer groups) and through assets assigned to users. *Recommended: both.*
7. **Change risk** (H3, H5): default approval path per risk level (low: the change manager; medium: the CAB; high: the CAB and an executive; emergency: the emergency board), editable by administrators; and the **predicted risk** from statistics of past changes' outcomes on the same CIs, class and team (a rule anyone can read, not a trained model), with the AI only explaining. *Recommended: as written.*
8. **CAB votes** (H4): votes are advice and the chair decides, or a majority decides? *Recommended: advice, the chair records the decision.*
9. **Known errors in the portal** (H1): publish a known error's workaround to the portal as an external knowledge article through D1's four-eyes review, rather than a separate publishing flow. *Recommended: through knowledge.*
10. **Trend detection** (H2): default rule for proactive problems: a category, CI or service with at least 10 incidents in a month and at least twice its average of the three months before; suggestions only, never automatic problems. *Recommended: as written, editable in Settings.*
11. **New roles** (H1, H3, H4): problem manager, change manager and CAB member as permissions given to team leads and administrators by default, with custom roles (B2) for organisations that want named roles, so the six personas stay. *Recommended: permissions only.*
12. **CMDB size** (G1, L1): target number of configuration items per tenant for the server sizes, to include in the load test: *recommended 50,000 on Small, 500,000 on Medium.*
13. **Offline-friendly scope** (J1): the app opens offline, shows the requester's own last-viewed tickets read-only (cached on the device, cleared at sign-out), and keeps unsent new tickets and replies on the device until the connection is back; agents' queues are never cached; a tenant setting can turn offline data off. *Recommended: as written.*
14. **Web push network** (J2): push goes through the browsers' push services (Google, Mozilla, Apple, Microsoft), so the server needs outgoing HTTPS to them; air-gapped installations get no push and keep email, in-app and Teams. Zelvo's own implementation of the push protocols (no new library), as with the AI clients. *Recommended: as written.*
15. **Passkeys** (J3): passkeys through Keycloak's built-in WebAuthn, counted as staff's second factor when the device verified the person. *Recommended: yes.*
16. **Barcode scanning** (G3): the browsers' built-in barcode reader is missing on iPhones, so a small scanning library (ZXing-based, MIT or Apache-2.0, licence checked before adding) is needed; labels carry the asset tag only (QR and Code 128), not an address. *Recommended: as written.*
17. **Teams app scope** (J4): personal tab, "Raise a ticket" dialog and message action as listed. *Recommended: as written.*
18. **Plain-language rules** (K1): the administrator who wrote the rule approves it (no second person), and the AI feature is off until set up like the other AI features. *Recommended: as written.*
19. **VIP** (K1): use B3 customer groups ("VIP") for the requirement's example rather than a new VIP flag on people. *Recommended: customer groups.*
20. **Custom record types and app builder scope** (K2, K3): record types on the ticket core (states mapped to the core's state categories) plus simple data lists, apps exported and imported as JSON packages, no custom code until module 28. *Recommended: as written.*
21. **Wellbeing details** (K4): who sees individuals (team leads for their own groups; executives and administrators group totals only, not individuals), off by default, 90 days of daily figures, after-hours measured from Zelvo activity only, and agents see the same alerts about themselves that their team lead sees. *Recommended: as written.*
