# Cryptographic inventory and key management (task F7)

Every key, secret, certificate and cryptographic algorithm Zelvo uses, and the policy for managing them. Covers OWASP ASVS 5.0 V11.1.1 (key management policy), V11.1.2 (inventory), V11.1.3 (discovery of cryptographic mechanisms) and V11.1.4 (inventory kept up to date). Related: `docs/architecture/secrets-encryption.md` (stored secrets), `docs/architecture/licensing.md` (vendor keys), `docs/architecture/security-baseline.md` (transport), `docs/architecture/communications.md` (connections), `docs/security/data-protection-levels.md` (what each key protects).

Checked against the code on 2026-11-26. "Compose" means `deploy/compose/compose.yaml` (development and small installs); the hardened install is task F6.

## Roles

| Role | Keys and secrets they own |
| --- | --- |
| **Product owner** (vendor) | The vendor signing key for licenses, upgrade licenses and update packages. Kept only on the product owner's own signing computer. |
| **Installation operator** | The master key file or Vault/OpenBao, service passwords in `.env`, the internal CA and service certificates, the public TLS certificate or ACME account, the installation mail server password, `ZELVO_TLS_TOKEN`, Keycloak's bootstrap administrator and client secrets. |
| **Tenant administrator** | Keys and secrets they enter or create in Settings: AI provider keys, mailbox, messaging, payment and connector credentials, webhook secrets, API keys and OAuth clients, uploaded custom-domain certificates, the DKIM key of their sender domain, UAE PASS and Entra client secrets. |

## Keys, secrets and certificates

"Data key" means the tenant's AES-256 data key from `Zelvo.Secrets` (`SecretProtector`). A value "encrypted with `Zelvo.Secrets`" is AES-256-GCM with the associated data `zelvo/secret/v1|<tenant>|<purpose>`, so it decrypts only for that tenant and that purpose (the purpose is given in the table).

## Key management policy

This policy applies to every row above. **Cryptoperiods marked "for the product owner to set" need the product owner's approval**; until then the rotation procedures exist but no period is mandated.

1. **Generation.** Keys are generated with the platform's cryptographic generator (above), at the place where they are used, never by hand and never copied from examples. Symmetric keys are at least 256 bits; RSA keys at least 2048 bits (3072 for vendor keys); ECDSA keys P-256 or stronger. Tests generate throwaway keys at run time; no key, license file or signed package is committed (`CLAUDE.md`).
2. **Distribution.** Private keys are not distributed: the vendor key stays on the signing computer, Vault keys stay in Vault, data keys leave the database only wrapped. Secrets reach containers as Compose secrets or environment variables from `.env` (F6 moves them to Docker or Kubernetes secrets). Tenant secrets are entered once over HTTPS and never returned.
3. **Storage.** Secrets Zelvo stores are encrypted with `Zelvo.Secrets`. Tokens Zelvo checks are stored as hashes. Nothing secret is written to logs, telemetry, the audit log or the integration log (`logging-inventory.md`). `.env`, `deploy/compose/secrets/`, `*.key` and `*.pem` are git-ignored and excluded from Docker build contexts (`.dockerignore`); Gitleaks runs in CI.
4. **Access and sharing.** Each key is used for the one purpose in its row, bound by the AES-GCM associated data (tenant and purpose) or the signed file type. A private key exists in one place only. A shared secret should be shared by two parties only. Known exceptions, to be fixed: the Valkey password (Valkey, API, web app), the application role's password (API, worker, updater) and the provisioner secret (Keycloak, migrate, API; migrate and API are the same image); separate Valkey users and an updater database role are proposed for F6 or earlier.
5. **Rotation.** Each row names its procedure. Rotations are audited where Zelvo performs them (`secrets.dataKeysRewrapped`, API key and webhook secret rotation, certificate upload). Certificates are renewed before expiry (internal: under 30 days left; ACME: by Caddy).
6. **Compromise.** Revoke or replace at once: API keys and OAuth clients are revoked in Settings → Integrations (effective immediately); webhook, gateway, messaging, connector and AI credentials are re-entered (the old value is overwritten); a suspected master key compromise means a new key file or Transit key, `rewrap-keys --retire-active`, then re-entering the tenants' secrets; a vendor key compromise means a new key in `vendor-keys.json` shipped as a security update package, removal of the old key and reissue of the affected licenses; a DKIM key compromise means changing the sender domain setting (new key and selector) and removing the old DNS record. Incidents follow the customer's incident process (`uae-ia-mapping.md`).
7. **Destruction.** Old master key files are deleted after `rewrap-keys`. Data keys are retired, not deleted, while values still use them (a trigger refuses deletes). Erased tenants' secrets are removed with their rows. Throwaway test keys exist only in memory. The vendor key file is destroyed by the product owner when its key id is retired.
8. **Keeping this inventory current.** A task that adds or changes a key, secret, certificate, algorithm or protocol updates this document and the ASVS checklist in the same pull request. The inventory is reviewed at each release (F6). New mechanisms are found by searching the code for `System.Security.Cryptography`, `RandomNumberGenerator`, `node:crypto` and `java.security` and by the CodeQL scans in CI.

## Known gaps

- Uploaded custom-domain certificates are checked for pair, validity and host but not for key size or signature algorithm (ASVS V11.6.1).
- Keycloak runs `start-dev` over plain HTTP inside Compose; its HTTPS protocols and suites are set in F6.
- PostgreSQL, Valkey, the Keycloak back channel and OTLP are plain inside the Compose network (F6; see `communications.md`).
- Web sessions in Valkey hold the access and refresh tokens in clear, protected by the Valkey password and network isolation only.
- The updater's backups (database dumps and copies of `.env`) are in the `updates` volume, which the API also mounts; they are not encrypted by Zelvo.
